# 开发过程与工作流复盘

作者记录：Codex 辅助开发，2026-11-17。本文为约 1–1.5 页篇幅的 Markdown 复盘；不宣称已使用 Claude Code，也不把 DeepSeek HTTP 替身测试说成真实请求验收。

## 从约束到可验证的产品

先将作业转成可观察的验收条件：用户确认阵容前不能开场；专家不能固定轮流；观点需要在讨论过程中更新；不同讨论不能共享状态；刷新不能重新启动任务。与用户确认的流程一致，先建立 Git 和 AGENTS.md，再保存产品、技术与实施方案。用户额度不足时停在文档阶段并推送仓库，恢复后从脚手架继续，没有重新生成或伪造历史。

SDD 阶段先定义 Pydantic 输入、角色、意图、发言与观点结构，以及讨论状态机和 SSE 游标。数据建模将讨论、嘉宾、消息、观点、事件分开，用 discussion_id 约束访问。模型输出被视为不可信输入：结构校验之后仍需检查人数、姓名重复和引用归属。后台 Runner 独立于观众连接，数据库承担历史和恢复，不把浏览器订阅当作任务启动器。

DDD 阶段按题目所指的组件/页面开发，先用样例完成首页、阵容确认和演播厅。实际采用 React、Zustand、Lucide 和原生 CSS，省去原计划中的 Tailwind/shadcn。完成 API 集成后移除静态预览分支，并拆成 Home、Roster、Studio、Avatar 组件；用独立滚动区域和移动标签页表达“现场感”。点击共识/分歧中的姓名可以定位原始发言，使 AI 输出具备可检查的上下文。

TDD 阶段先提交调度和证据测试，首次运行确实因实现模块不存在失败；随后实现确定性仲裁，再获得 9 项通过结果。专家分别判断是否举手、补充或反驳，调度器只负责公平性、紧迫度和连续发言限制。完整链路测试覆盖并发隔离、启动幂等、超时、无效输出与重启中断。E2E 使用真实 FastAPI/SQLite 和可控 DemoLLM，在桌面与手机视口运行，不通过浏览器 mock 整个后端来制造通过结果。

## 实际遇到的问题与修正

第一，本机预览进程输出了“ready”，但浏览器无法连接。通过端口检查与 HTTP 请求确认存在监听但连接超时，在正确网络权限下重启项目服务后返回 HTTP 200，再用浏览器验证。由此将“进程已启动”与“用户能访问”拆成两个验收步骤。测试客户端在受限本地套接字环境中也曾挂起；授权环境运行通过后清理旧进程，没有误报挂起测试为成功。

第二，Demo 中支持性发言使用“支持先验证”，提炼规则只匹配“优先验证”，漏掉本来已有证据的分歧。截图检查暴露这一点后修正规则，并增加种子讨论必须同时含有受支持共识与分歧的回归测试。真实模型模式仍依赖语义提炼，应用层只能保证引用存在与参与者数量，不能用 ID 校验替代内容质量判断。

第三，快照请求与实时事件可能交错，旧快照有覆盖新事件的风险。Zustand 拒绝倒退的序号，启动操作以持久化 SSE 作为状态更新来源；阵容重试通过重新订阅恢复，避免异步旧请求把用户带回上一场讨论。跨讨论消息和证据校验也放在服务端，不能只靠前端清空状态。

## 工程化 AI 开发的理解

AI 的价值在于快速生成候选实现，工程责任在于把候选实现限制在明确契约里，并用失败案例检验它。任务按模型边界、状态机、UI 和测试分阶段推进，每阶段记录实际产物与提交。用户后来限定只用 DeepSeek，便查询官方文档，落实模型名、JSON 模式、thinking 参数及空白/截断处理；没有沿用未经核实的兼容性假设。

当前交付提供可运行演示与真实 DeepSeek 适配器，未完成的是真实密钥下的质量/延迟验收和用户人工验收。后续应围绕真实模型的发言相关性、观点证据质量、请求延迟和成本调整提示词与预算，再考虑复杂基础设施，而不是把依赖数量当成完成度。
