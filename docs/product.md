# 产品需求与验收标准

本文定义产品目标与验收条件；实际完成状态见[交付清单](delivery.md)，执行结果见[测试与验收记录](verification.md)。

## 1. 产品定位

AI Panel Studio 帮助用户从多个立场审视同一议题。主持人负责开场、追问、串联和总结；专家根据讨论内容自主表达意图、补充或反驳。用户作为观众，能够看到讨论过程、观点变化及其发言依据。

目标用户包括时间有限的知识工作者、需要评审方案的产品与决策人员，以及希望获取结构化讨论材料的教育与内容创作者。

## 2. 用户流程

1. 首页浏览已有讨论，加入进行中的讨论或查看历史。
2. 输入 4–240 字的话题，选择 2–6 位专家，默认 4 位；另配 1 位主持人。
3. 查看主持人与专家的姓名、职业、Title、立场及专属颜色，确认后开场。
4. 演播厅展示嘉宾状态、公开关注点和实时发言；过程中的共识与分歧可以定位到原始发言。
5. 主持人总结后结束，历史记录保存在本地。

2–6 位专家是当前 MVP 的实现范围，不是原题规定的上限。Demo 使用预设规则；live 调用模型。两种模式明确标识，live 出错时不自动替换成演示内容。

## 3. 页面与交互

| 页面 | 内容与行为 |
| --- | --- |
| 首页 | 话题输入、人数选择、生成入口、讨论列表与状态；按分类每页 20 场，可前后翻页 |
| 阵容确认 | 主持人与专家卡片、立场和颜色；确认开始；生成失败时重试 |
| 演播厅 | 顶部话题和连接状态，左侧嘉宾，中间发言，右侧共识与分歧；结束后显示总结 |

界面使用中文、浅暖灰背景、白色卡片和深绿品牌色。专家颜色在嘉宾卡、发言和证据入口保持一致。

桌面采用独立滚动的三栏；小屏使用“现场 / 嘉宾 / 观点”标签。新发言自动跟随，用户回看历史时暂停跟随并显示新发言入口。Transcript 仅展示实际发言，不包含内部举手、评分或模型原始 JSON。

## 4. 功能验收标准

| 编号 | 功能 | 验收条件 |
| --- | --- | --- |
| P01 | 讨论首页 | 可以发起讨论、加入已有讨论；种子至少 5 组；原题要求展示全部进行中讨论 |
| P02 | 嘉宾生成与确认 | 默认 4 专家 + 1 主持人，字段完整且姓名不重复；确认前不能开场 |
| P03 | 主持人 | 开场、追问/串联、最终自然语言总结可见 |
| P04 | 自主调度 | 专家根据当前内容提交意图；不存在固定轮流发言名单 |
| P05 | 短发言 | 专家每次目标 1–2 句；应用校验句数与最大长度 |
| P06 | 状态与隐私 | 等待、准备、发言状态和公开关注点可见；不展示隐藏思维链 |
| P07 | 过程观点 | 结束前更新共识/分歧；证据属于本讨论且涉及至少两位专家 |
| P08 | 实时通信 | 不刷新也能收到发言、状态和观点 |
| P09 | 多讨论隔离 | 两场同时运行时，任务、消息、状态、观点与事件不串台 |
| P10 | 加入与刷新 | 加入、刷新恢复已有内容，不重复开场、不重复显示消息 |
| P11 | 总结 | 主持人以自然语言总结，不显示 JSON 原文 |
| P12 | 响应式 | 宽屏、普通桌面、小屏均能使用核心操作，各区域合理滚动 |
| P13 | 异常处理 | 生成失败、模型超时、连接重试有提示；请求和讨论有预算 |
| P14 | 本地运行 | 按指南启动前后端、初始化 SQLite；密钥仅在后端环境变量 |

证据 ID 有效不能证明语义正确，真实模型的相关性、反驳质量与共识依据仍需人工检查。响应时间与费用不作未经测量的承诺。

## 5. 演示数据

[种子脚本](../backend/app/seed.py)提供以下五组话题，每组含 1 位主持人和 4 位立场不同的虚构专家：

1. 小型软件团队应优先使用 AI 编程工具还是增加招聘？
2. 企业是否应实行每周四天工作制？
3. 高校课程应如何允许学生使用生成式 AI？
4. 初创产品应先增长还是先盈利？
5. 城市中心是否应限制私人汽车通行？

首次初始化时第一组为保存的已结束示例，另四组为待确认阵容。所有种子标记为 Demo；不预置假运行任务。重复初始化不重复插入。

## 6. 范围与约束来源

本次为 24 小时预算的本地面试 MVP；原题提交段落写 72 小时，开发按用户预算安排。流程为 Git/协作约定 → 产品方案与 Demo → 技术设计 → 编码与 AI 自测 → 用户人工验证。

暂不包含登录、付费、云部署、语音、联网检索、知识库、多人共同编辑和复杂 Agent 框架。原题工具要求、交付文件要求与当前差距集中列在交付清单。
